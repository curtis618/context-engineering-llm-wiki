為什麼

資料給越多，AI 就越聰明嗎？

一般假設模型會平均地使用整段上下文，實驗顯示不是。

  • 上下文視窗已經大到 1M token，但更長的上下文不會產生更好的回答
  • 輸入越長，模型的表現越不可靠
  • 對話記憶測驗：只給相關片段（約 300 token）的表現，明顯高於給完整歷史（約 113k token）

視窗變大，不等於回答變好。

為什麼

視窗是有限的工作記憶

Karpathy 的比喻：LLM 像作業系統，模型是 CPU，上下文視窗是 RAM，也就是模型的工作記憶。

  • 視窗裡裝三類東西：指令、知識、工具回傳的結果
  • 上下文是有限資源，而且邊際效益遞減：放越多，每一份新增內容的幫助越小
  • 模型有「注意力預算」，每多一個 token 就會消耗一點

為什麼

實驗證據：Context Rot

Chroma 測試了 18 個模型（包含 GPT-4.1、Claude 4、Gemini 2.5、Qwen3 系列），任務刻意保持簡單，只改變輸入長度。

  • 干擾句（和問題相關但不是答案的句子）：只加一個，表現就比沒有干擾時差；加到四個更差
  • 文章結構：順序正常、前後連貫的長文，反而比句子被隨機打亂的長文更難找到答案，18 個模型都是如此

輸入越長，表現越不可靠，即使任務本身很簡單。

怎麼做

好的上下文長什麼樣子？

Anthropic 的核心原則：找出最小的一組高訊號 token，讓想要的結果最可能發生。

  • 系統提示：寫在「剛好的高度」，不要寫成死板的 if-else 規則，也不要寫成空泛的指示
  • 精簡不代表短：先用最少的提示測試，再根據實際出錯的地方補上指令與範例
  • 工具：避免太多、選擇模糊不清。人類工程師都說不出該用哪個工具，agent 也做不到
  • 範例：不要塞一長串特殊情況，挑少量、多樣、有代表性的例子

怎麼做

四種策略：存、取、縮、分

寫入 Write：

把資訊存到視窗外面，需要時再用。例如 agent 把筆記寫進待辦清單或 NOTES.md，之後再讀回來

選取 Select：

把需要的資訊拉進視窗。只保留檔案路徑、網址這類輕量的索引，需要時才載入內容

壓縮 Compress：

只保留完成任務所需的 token。對話快到視窗上限時先摘要，再用摘要開一個新視窗

隔離 Isolate：

把上下文拆開分頭處理。子代理各自探索，只回傳濃縮過的摘要，通常是 1,000-2,000 個 token

實務

實戰：Manus 團隊的心得

作者的經驗：在 BERT 的年代微調模型，每次改動可能要等幾週；用 context engineering，改進可以在幾小時內上線。

  • 圍繞快取設計：輸入輸出 token 比例約 100:1；以 Claude Sonnet 為例，每百萬 token 有快取 0.30 美元、沒快取 3 美元
  • 靠複誦控制注意力：一個典型任務約 50 次工具呼叫，agent 容易忘記目標；讓它反覆改寫 todo.md，把目標放回上下文最後面
  • 把錯誤留下來：不要清掉失敗的動作與錯誤訊息，模型看到失敗的結果才會調整
