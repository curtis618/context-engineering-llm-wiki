# 好的上下文長什麼樣子

> 一句話：資訊要充足，但要精簡；目標是「最小的一組高訊號內容」。

## 核心原則

- 找出最小的一組高訊號 token，讓想要的結果最可能發生。 [S5]
- 整體要求是：資訊充足，但保持精簡。 [S5]
- 在檢索策略上，建議從最簡單可行的方式開始。 [S5]

## 系統提示（system prompt）

- 要寫在「剛好的高度」：不要寫成死板的 if-else 規則，也不要寫成假設對方都懂的空泛指示。 [S5]
- 用分段來組織，例如 XML 標籤或 Markdown 標題。 [S5]
- 精簡不代表短。先在最好的模型上用最少的提示測試，再根據實際出錯的地方補上指令與範例。 [S5]

## 工具

- 工具回傳的內容要節省 token。 [S5]
- 避免工具太多、選擇模糊不清。如果人類工程師都說不出某個情況該用哪個工具，agent 也做不到。 [S5]

## 範例

- 仍然強烈建議提供範例，但不要塞一長串特殊情況，而是挑少量、多樣、有代表性的例子。 [S5]

## 相關說法：範例與模仿

- Anthropic 仍強烈建議提供範例，條件是少量、多樣、有代表性。 [S5]
- Manus 提醒 few-shot 在 agent 裡可能適得其反：模型會模仿上下文裡「動作與結果」的模式，陷入固定做法；解法是在格式與措辭上加入少量變化。 [S6]
- 這兩個說法出自不同文章，這裡只並列。 [S5][S6]
